# Первое подключение школы

Этот порядок подготавливает локальную производственную базу и первого взрослого администратора. Он не размещает приложение, не подключает webhook, не отправляет сообщения MAX и не проверяет реальную доставку.

## Кто может выполнять подключение

Оператор школы должен отдельно проверить взрослый статус ответственного, его полномочия и точный MAX ID. CLI не определяет возраст по имени и не подтверждает принадлежность аккаунта человеку. Сам пользователь может узнать свой MAX ID командой `/identity` в боте.

Первичный CLI работает только с новой базой либо пустой базой текущей схемы. Он не повышает существующих учеников/кураторов и не переносит MAX ID между школами. Уже совпадающий активный администратор даёт результат `noop`; другое имя, школа, роль или отозванный доступ требуют отдельного штатного администрирования.

Перед работой остановите сервис. Существующая SQLite-база должна быть штатно закрыта и не иметь незавершённого WAL. Не удаляйте `-wal`/`-shm` вручную. Этот CLI не обновляет старые схемы и не использует демонстрационных пользователей.

## Предварительный просмотр

Значения ниже **вымышленные**, это пример синтаксиса, а не разрешение назначать права. Подготовьте защищённый каталог базы. Не кладите базу в Git и не используйте символическую ссылку как путь.

```sh
python3 -m vneurok.school_setup \
  --db /защищённый/каталог/school.db \
  --school-id synthetic-school \
  --school-name 'Синтетическая школа' \
  --admin-name 'Синтетический взрослый' \
  --admin-max-id 900000001
```

Без `--apply` это только preview: база и её каталог не создаются, SQL-миграции и назначения прав не выполняются. Для существующей базы preview не создаёт даже служебные WAL/SHM-файлы. Предварительный результат не блокирует дальнейшие изменения другими процессами; при записи условия проверяются заново в транзакции.

## Явная запись после проверки

Только после проверки конечной школы, имени и MAX ID повторите ту же команду, добавив одновременно:

```text
--apply --confirm-access --confirm-adult
```

`--confirm-access` подтверждает полномочия указанного человека управлять указанной школой. `--confirm-adult` означает, что оператор независимо подтвердил взрослый статус. Создаются права `curator`, `is_admin=1`, класс `staff`, без других участников и школьных данных.

Новая база полностью собирается во временном файле в том же каталоге и публикуется атомарно без перезаписи существующего файла; права нового файла — `0600`. В существующей базе изменение выполняется одной транзакцией. Аудит записывается в `admin_history` и `school_setup_audit` вместе с отметками явных подтверждений. Ошибка записи не даёт основания автоматически пробовать другого пользователя или другую школу.

Одинаковый повтор не создаёт второго администратора и не дублирует аудит. Если результат процесса потерян, сначала повторите preview. Не меняйте исходные параметры лишь для обхода конфликта.

После запуска первый администратор входит через подтверждённый MAX-аккаунт. В панели школы он добавляет классы, помещения и интервалы, назначает ответственных, задаёт срок хранения и создаёт именные приглашения. Коды привязаны к конкретному MAX ID. Пользователь не выбирает себе взрослую роль.

## Локальный healthcheck

```sh
APP_ORIGIN=https://ваш-проверенный-домен python3 -m vneurok.healthcheck
```

Проверка всегда соединяется **только с `127.0.0.1:8765/health`**, передавая публичный Host из `APP_ORIGIN`. Токены не читаются и не передаются, прокси и редиректы не используются, обращения к MAX нет. Успех означает работающий HTTP-процесс в школьном режиме, а не исправную доставку, настроенный TLS или корректность всех данных. Для другого локального порта используйте `--port`; демонстрация допускается только с отдельным `--allow-demo`.

Dockerfile объявляет эту же проверку каждые 30 секунд, timeout 5 секунд, start period 20 секунд, три неуспешные попытки. При стандартном запуске контейнер использует внутренний порт 8765. Смена порта требует согласованной смены healthcheck.

## Что фактически проверено локально

```sh
python3 scripts/run_tests.py --pattern test_school_setup.py
python3 scripts/run_tests.py --pattern test_healthcheck.py
python3 scripts/run_tests.py --pattern test_startup_smoke.py
```

Тесты используют только временные файлы, вымышленные личности и синтетические настройки. Startup smoke действительно запускает `python -m vneurok.server --max-mode` на loopback отдельным процессом **без `--send-enabled`**, проверяет HTTP `/health`, отсутствие демонстрационного входа, ограничения авторизации и сохранение первичного администратора после остановки и повторного запуска.

Строгий runner дополнительно считает ошибкой `ResourceWarning` из финализаторов. Обычного `-W error::ResourceWarning` недостаточно: Python может вывести ошибку финализатора и завершиться с кодом 0.

## Что подготовлено, но здесь не выполнялось

`.github/workflows/check.yml` содержит Python 3.12/3.14 + Node проверки и отдельный Docker smoke: новая синтетическая школа в постоянном volume, `--network none`, школьный HTTP-запуск, реальный restart, повторные проверки сохранности и встроенный HEALTHCHECK. Контейнер не публикует порты и не включает отправку MAX. GitHub Actions и публикация артефакта выполнятся только после отдельно разрешённой публикации изменений и запуска workflow.

На текущем Mac Docker отсутствует. Образ не собирался и контейнерный сценарий здесь не выполнялся. Успешный локальный subprocess не заменяет Docker/CI-проверку. Реальные права, credentials, сервер, TLS, webhook, клиент MAX и реальные школьные данные требуют отдельного разрешённого этапа.
