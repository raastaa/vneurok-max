- Автоматические кейсы выполняются на новых временных SQLite-базах, вымышленных людях/школах и подменённом MAX transport. Результаты окончательного прогона и точные имена тестов находятся в [TEST_RESULTS.json](TEST_RESULTS.json).
- **Локальный PASS не означает доставку в MAX.** Реальные токены, детские аккаунты, webhook, TLS выбранного хоста и опубликованный образ не использовались.
- Отдельно проведён локальный визуальный проход в Chrome, окно 390×844: создание черновика, дополнение и «без помещения», без горизонтального переполнения. Остальные веб-сценарии проверены DOM-тестами, не глазами в каждом клиенте MAX.
- Исторический первый аудит имел 87 тестов. Для текущей версии использовать новый журнал, а не это старое число.

## Подготовка синтетических данных

Временная школа A: два класса 7А и 8Б, три пространства, учебные автор/помощник/участник, куратор и отдельный администратор. Для отрицательных проверок добавляются 7Б, школа B и её взрослый/ученики. События создаются в будущем внутри разрешённого интервала; прошлое время задаётся только в изолированных тестах для проверки итога. Ни один MAX ID в тестах не является разрешением писать реальному человеку.

Запуск:

```sh
python3 scripts/run_tests.py
python3 scripts/verify.py --output docs/TEST_RESULTS.json
node --check web/app.js
node tests/test_web_guided.js
python3 -m compileall -q vneurok tests scripts
git diff --check
```

Не запускать `.env`, не включать `--send-enabled` с реальными секретами ради автоматических тестов.

## Сквозные процессы

### TC01. Автор доводит событие до подтверждённого итога

**Перед:** школа настроена, помещение имеет ответственного и доступный интервал. Автор, помощник, посетитель и куратор различны.

1. Автор сохраняет только название. Закрывает и заново открывает приложение.
2. Приглашает помощника, создаёт задачу; помощник берёт её до согласования.
3. Автор дополняет цель, аудиторию, тему, время, место и количество мест; отправляет заявку.
4. Куратор возвращает замечание. Автор исправляет и подаёт повторно.
5. Ответственный куратор согласует; автор открывает запись; посетитель записывается.
6. После начала куратор явно выбирает «пришёл» или «не пришёл». После конца автор пишет итог.
7. Куратор подтверждает факт проведения.

**Ожидается:** одна карточка и история; отдельные membership/task/follow/registration/attendance; booking approved после согласования; completed только после итога и посещаемости. **Проверка:** core whole_flow, request_changes, helper_task; critical result/confirmation; bot guided. **Реальный MAX:** не выполнен.

### TC02. Небольшая закрытая встреча

**Перед:** kind=team, автор и приглашённый помощник.

1. Собрать команду и задачу, выбрать время и помещение либо no-room.
2. Отправить/согласовать без открытия публичной записи.
3. Проверить чтение другим учеником во всех статусах: draft, submitted, approved, awaiting_confirmation, completed, cancelled.
4. Подать итог и отдельно подтвердить проведение, отметив фактическое участие команды.

**Ожидается:** посторонний никогда не получает состав/описание/задачи; /join запрещён; инициатор входит во вместимость; итог не подтверждается самим автором. **Проверка:** critical team privacy/capacity, school isolation, domain team attendance. **Предел:** это синтетическая встреча, не школьный пилот.

### TC03. Полный сценарий без помещения

Выбрать needs_space=false, не передавать space_id, указать время/места, отправить и согласовать. Создать вторую инициативу в то же время без помещения. **Ожидается:** booking_status=not_required; нет фиктивной брони и ложного конфликта комнаты; остальные роли и итог сохраняются. **Проверка:** domain no_room + bot plan + мобильный браузер.

## Подключение школы и безопасность входа

### TC23. Первое подключение администратора

На отсутствующей БД выполнить preview school_setup. Проверить, что файл/каталоги не созданы. Попытаться apply без подтверждений взрослого и доступа. Затем на синтетических параметрах выполнить явный apply; повторить его. Попробовать использовать занятый MAX ID или повысить существующего неадминистратора.

**Ожидается:** preview без записи; недостающие подтверждения блокируют; ровно один назначенный администратор; отказ перезаписи/самоповышения. **Проверка:** school_setup suite. Реальное назначение взрослого не выполнялось.

### TC24. Именное приглашение

Администратор школы A выдаёт код для заранее известного MAX ID, имени, роли student/curator и класса. Проверить подстановку другого MAX ID, школы, роли admin, просрочку, отзыв, повторное и одновременное погашение, отзыв прав выдавшего взрослого.

**Ожидается:** в БД только хеш; код действует лишь своему аккаунту и школе; новый пользователь не получает is_admin; один профиль при повторах; все недействительные случаи отвергаются. **Проверка:** 12 onboarding cases, HTTP signed enrollment, guided /school.

### TC25. Подпись, сеанс, CSRF и закрытые данные

Изменить один символ initData, дублировать hash/user/WebAppData, использовать старое/будущее время, чужой Origin/Host или POST без CSRF. После входа администратор меняет класс/роль/active; повторить старый сеанс и отложенный ответ бота.

**Ожидается:** подпись/параметры отвергнуты; данные не попадают в URL/хранилище/логи; старые права не оживают. **Проверка:** MAX validation, HTTP access_changed, DOM duplicate params, bot reply guards.

## Матрица уведомлений

Сообщение всегда проходит фильтр своей школы, текущей аудитории, активного пользователя, актуальных условий и текущего основания подписки. Оно не заменяет серверный статус или повторную запись.

| Изменение | Кому и зачем | Что не допускается |
|---|---|---|
| Приглашение/назначение задачи | Приглашённому/исполнителю; автору о движении задачи | Рассылка всем детям, чужая школа |
| Подача | Уполномоченным кураторам школы | Ученик как согласующий |
| Решение/отложено/отказ | Автору и разрешённым участникам процесса | Публикация несогласованной редакции |
| Согласование/открытие записи | Команде, followers и opt-in подписчикам соответствующей темы/аудитории | Автоматическая запись или расширение аудитории темой |
| Запись/отказ от записи | Самому участнику и автору | Старое подтверждение после отмены регистрации |
| Перенос/изменение ресурса | Прежним участникам: прежняя запись снята, нужна проверка | Закрытые новые title/time/room в минимальном уведомлении |
| Сужение аудитории | Исключённому прежнему участнику той же школы: только факт отмены участия | Доступ к новой карточке или будущие тематические сообщения |
| Отмена | Разрешённой аудитории процесса | Повторное сообщение «запись подтверждена» из старой очереди |
| Итог/подтверждение | Куратору на проверку; после подтверждения участникам процесса | Авторский итог как доказательство фактического проведения |

### TC26. Подписки и отказ

Подписаться на technology, согласовать event этой темы и другой темы; создать private team; отказаться от темы. Отдельно follow/unfollow карточку во время повторного согласования. **Ожидается:** только нужная тема в своей аудитории; никакой private team рассылки; opt-out сохраняется после restart и отменяет недоставленные тематические сообщения. Активную запись сначала снимают, чтобы важные изменения не потерялись. **Проверка:** domain interest + critical optout + isolation.

### TC27. Устаревшая blocked/uncertain очередь

1. Участник без MAX mapping записывается, flush переводит уведомление в blocked.
2. Автор меняет время или отменяет событие. Для переноса повторно согласовать/открыть, но не записывать участника заново.
3. Администратор связывает MAX ID; выполнить flush с подменённым транспортом.
4. Повторить со старым failed и uncertain; попробовать вручную разрешить retry.

**Ожидается:** ни одно старое «запись подтверждена» не отправлено. У uncertain остаётся неопределённый исход и аудит; повтор старого смысла запрещён. Новый безопасный notice не раскрывает закрытую редакцию. **Проверка:** regression suite уведомлений и delivery `_permission`. Это обязательный gate перед живым MAX.

### TC28. Отзыв доступа после подготовки ответа

Подготовить ответ /view закрытой команды; до отправки удалить helper или изменить класс. Отдельно изменить права между render и enqueue. **Ожидается:** cancelled=1, sent=0; нельзя присвоить старому тексту новый снимок прав. **Проверка:** delivery prepared_card/render_snapshot; независимо повторено на BotRouter.

### TC29. Ограничение MAX и неопределённый исход

Возвратить transport HTTP 429 + Retry-After; проверить отсутствие раннего повтора, restart и ограничение числа попыток. Затем DNS/refused, timeout, 503, 401, TLS certificate failure и crash после claim.

**Ожидается:** 429 и доказанный preconnect повторяются безопасно; timeout/5xx/crash → uncertain без автоматического повтора; 401/TLS → failed без обхода проверки сертификата; бронь сохранена. **Проверка:** delivery reliability suite.

### TC30. Разбор неопределённой доставки

Студент, обычный куратор и администратор другой школы пробуют открыть/разрешить чужую очередь. Свой администратор пробует retry без галочки/заметки и mark_delivered без message ID, затем выполняет синтетически подтверждённое действие.

**Ожидается:** права/доказательства обязательны, действия журналируются. Панель не показывает тело сообщения/секреты. Sent/cancelled не предлагаются к повтору. **Проверка:** delivery/DOM reconciliation.

## Обязательная внешняя приёмка (пока НЕ ВЫПОЛНЕНО)

**E01. Хост и конфигурация.** Владелец выбирает отдельный хост, разрешает постоянный том и хранение секретов. Проверить HTTPS:443, доверенную цепочку, Host forwarding и исходящий TLS MAX. Не отключать проверку сертификатов. Токен вводится владельцем в защищённой форме/локально, не в чате.

**E02. Правильный бот/webhook.** Через разрешённый токен проверить /me и текущие subscriptions, затем согласовать единственный webhook с правильным secret, bot_started/message_created. Не создавать дубли и не менять чужой работающий бот.

**E03. Два взрослых аккаунта.** Получить разрешение именно на тестовые сообщения этим аккаунтам. Проверить /start, кнопки, /demo, изоляцию двух demo, перезапуск и отсутствие дублей. Учебный герой не равен реальному школьнику.

**E04. Mini-app MAX.** На целевых мобильном и web клиентах открыть приложение из MAX, signed login, cookies/CSRF, Bridge, возврат/закрытие, повторный вход; выполнить TC01–TC03 с назначенными тестовыми ролями. Обычный Chrome не заменяет этот шаг.

**E05. Реальная доставка.** На разрешённых тестовых получателях подтвердить уведомления о переносе, новом согласовании, отмене и итоги. Сверить message ID и отсутствие дублей. Тайм-аут не трактовать как недоставку.

**E06. Исправленный выпуск.** Публикация только после разрешения; зафиксировать commit SHA, успешный CI и новый образ/архив, SHA-256, размер, платформу, проверку запуска другим участником. Проверить отсутствие `.env`, баз и личных данных в Git и слоях. Старый v0.1.0 не выдавать за новый.

**E07. Школьный регламент.** Ответственный взрослый утверждает роли, пространства, инструктаж и правила хранения/удаления. При необходимости автоматического purge это отдельное условие до реальных данных.

**E08. Пилот и измерения.** Только с разрешёнными участниками провести интервью и одну–две инициативы. Записать числитель/знаменатель: приглашены, начали, подали, согласованы, записались, пришли; отдельно активное время автора/куратора и ожидание. Не выдавать целевые ≤3/≤1 минуты, планы опроса или синтетические события за реальные результаты.

## Шаблон ручного журнала

Для каждого E-кейса записать: дата/часовой пояс; версия/commit; устройство/клиент; тестовая роль без лишних персональных данных; шаг; ожидаемое; фактическое; PASS/FAIL/BLOCKED/NOT RUN; ссылка на разрешённый артефакт; дефект и повторная проверка. Секреты и необезличенные сообщения детей в журнал не копировать.
