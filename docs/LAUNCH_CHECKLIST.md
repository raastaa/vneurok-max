## Решение владельца

Нужны выбранный постоянный сервер и отдельный HTTPS-адрес на порту 443. Нельзя занимать порт работающего проекта или менять его reverse proxy без проверки. До настройки владелец подтверждает, где будет храниться токен и что можно включить ответы бота. Токен не присылается в чат, GitHub, журналы или командную строку.

Для сохранения токена владелец может самостоятельно выполнить `python3 scripts/configure.py` непосредственно на выбранном сервере. Скрипт принимает ввод скрыто и создаёт `.env` с правами 600, не отправляя запросов. Само наличие скрипта не означает, что настройка уже выполнена. Размещение учётных данных помощником требует отдельного подтверждения на этот шаг.

## Перед внешним подключением

1. Проверить ресурс сервера, архитектуру, свободный локальный порт, резервную копию конфигурации reverse proxy и место для отдельного тома базы. Проверенный образ a216b3d рассчитан на Linux amd64; для ARM нужен собственный образ.
2. Проверить домен, HTTPS и полную цепочку доверенного сертификата. MAX принимает webhook только на 443. HTTPS-proxy должен сохранять исходный Host. До активации отвечает `/health` с `demo: false`.
3. Проверить исходящее TLS-соединение с `platform-api2.max.ru`. Не отключать проверку сертификатов. Если нужна новая цепочка доверия, согласовать её отдельно.
4. После безопасной настройки выполнить `python3 -m vneurok.readiness --env-file .env`. Проверка показывает только названия проверок и результат. Она не доказывает доступность API или права токена.
5. Проверить принадлежность токена нужному боту через GET `/me`, не выводя токен. Проверить существующие подписки до добавления новой, чтобы не создать второй обработчик.
6. Только после разрешённого подключения настроить `/api/max/webhook` для `bot_started` и `message_created` с совпадающим секретом и включить `--send-enabled`. Команда Docker Compose использует этот флаг по умолчанию: это уже реальные ответы, не сухая проверка.

## Приёмка с аккаунта взрослого

Полные кейсы и отметки того, что действительно выполнено: [TEST_SCENARIOS.md](TEST_SCENARIOS.md). Настройка первого администратора и именных приглашений: [SCHOOL_SETUP.md](SCHOOL_SETUP.md). Старый опубликованный v0.1.0 не содержит исправлений. Для проверки нужен образ a216b3d.


Проверить весь путь, записав время, результат и замечания:

1. `/start`, `/help`, `/demo`, `/list`: бот отвечает в настоящем MAX.
2. Открыть карточку по `/view ID`. Автор отправляет её через `/submit ID`.
3. Переключить только учебного героя: `/role curator`, согласовать `/approve ID`.
4. `/role author`, открыть запись `/open ID`; `/role participant`, записаться `/join ID`.
5. Повторить запись: число участников не увеличивается. Проверить отмену `/leave ID`.
6. Через `/demo_end ID` показать окончание, затем `/result ID итог` от автора. Куратор явно отмечает `/attend ID USER да` или `нет` каждому участнику и выполняет `/confirm ID`. Это учебный результат, не реальное проведённое событие.
7. Второй взрослый открывает собственный `/demo`: не видит записи первого. `/school` без приглашения недоступен. Ученик не может назначить себе роль педагога в школьном режиме.
8. Перезапуск сервиса сохраняет данные. Повторная доставка одного webhook не создаёт второе действие. Неясный исход отправки требует сверки, а не слепого повтора.

Если шаг не пройден, не обозначать его готовым. Для контейнера проверить не только импорт Python, но и HTTP-старт, подключение тома, перезапуск и получение события MAX.
