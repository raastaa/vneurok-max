# Подключение MAX: подготовлено, не активировано

## Проверенные первичные источники (7 ноября 2026)

- Подпись входа: https://dev.max.ru/docs/webapps/validation
- Bridge и `initData`: https://dev.max.ru/docs/webapps/bridge
- Отправка сообщений: https://dev.max.ru/docs-api/methods/POST/messages
- Webhook и секрет: https://dev.max.ru/docs-api/methods/POST/subscriptions/

Конкурсная история отдельно предусматривала получение токена через «Идея фикс». Фактическое право команды на доступ и текущий конкурсный порядок нужно подтвердить перед подключением. Обычный производственный доступ и конкурсный доступ не считаются автоматически одинаковыми.

## Что сделано в коде

Вход MAX использует исходную строку `initData` и двухэтапную HMAC-SHA256 с ключом `WebAppData`, сравнение в постоянном времени, запрет повторяющихся параметров, максимальный возраст один час, запрет будущей даты. `initDataUnsafe` не является источником полномочий. После проверки MAX ID сопоставляется с заранее внесённой записью `users.max_id`; роль хранится только в БД. Автоматической регистрации ученика, повышения роли или чтения контактов нет.

Webhook `POST /api/max/webhook` проверяет `X-Max-Bot-Api-Secret`. Поддержаны `bot_started` и личные текстовые команды маршрута из `/help`, включая `/demo`. Входящее событие само не отправляет ответ: он сохраняется в `bot_outbox` и дедуплицируется. Групповые сообщения и другие типы событий игнорируются. Тесты используют вымышленные значения.

## Что потребуется перед реальным пробным запуском

1. Разрешённый токен бота, HTTPS-домен и согласованное подключение. Секреты передаются через защищённую настройку окружения, не через чат и не через репозиторий.
2. Отдельная пустая база для режима MAX. Для конкурсного `/demo` приглашения в школу не нужны: каждому MAX ID создаётся собственный вымышленный пример. `/school` доступен только заранее приглашённым пользователям с назначенными ролями. Не переносить учебные роли в настоящую школу.
3. Надёжный HTTPS reverse proxy на порту 443 перед Python-сервисом. Настроить совпадающий `APP_ORIGIN`, передавать исходный Host, ограничить размер/частоту запросов и таймауты. Нестандартные порты и самоподписанные сертификаты для webhook MAX не подходят.
4. Настроить webhook для `bot_started` и `message_created` после проверки HTTPS. Адрес мини-приложения нужен отдельно для веб-интерфейса, но для текстового учебного маршрута не обязателен. Действия пока не выполнены.
5. Проверить вход, cookies и переход из MAX на целевых клиентах. Мини-приложение извлекает `WebAppData` из URL-фрагмента и очищает его, либо использует уже предоставленный `window.WebApp.initData`. Внешний скрипт Bridge сейчас не загружается.
6. Отдельно разрешить тестовую отправку уведомлений выбранным взрослым аккаунтам и проверить доставку.

## Запуск после подготовки

```sh
# Переменные должны уже находиться в защищённом окружении:
# APP_ORIGIN=https://ваш-проверенный-домен
# MAX_BOT_TOKEN=...
# MAX_WEBHOOK_SECRET=...
python3 -m vneurok.server --max-mode --db data/pilot.db
```

В `--max-mode` сервер отказывается запускаться без HTTPS origin, токена и секрета webhook. Демо-вход отключён. Токен никогда не попадает в JavaScript или URL запросов к MAX. Нужна отдельная проверка production-контура; один флаг не делает прототип готовым к работе с детьми.

## Очередь сообщений

Безопасная проверка без отправки:

```sh
python3 -m vneurok.notifications --db data/pilot.db
```

Флаг `--send` делает реальные внешние запросы. Этот флаг относится к отдельной очереди школьных уведомлений. Сам сервер с `--send-enabled` автоматически обрабатывает и ответы бота, и школьную очередь. В Dockerfile этот флаг уже включён: контейнер нельзя запускать с настоящим токеном до согласованного подключения. Его можно использовать только после разрешения на тестовое подключение и соответствующие сообщения.

Отправка фиксирует `sending` до сети. Таймаут, сетевой обрыв или неподтверждённый ответ оставляют `uncertain`; остановка процесса в момент отправки оставляет `sending`. Ни одно из этих состояний не повторяется автоматически. Сначала нужно сверить фактическую доставку. Однозначный HTTP 4xx сохраняется как `failed`, успешный ответ с сообщением как `sent`. Статус брони при этом не меняется. Production-панель разбора ошибок и правила сокращения устаревшей очереди пока не реализованы.

## Контейнер

`Dockerfile` и `compose.yaml` предназначены для будущего режима MAX. Порт опубликован только на 127.0.0.1, контейнер работает без root, файловая система read-only кроме volume базы. Образ собран и проверен в GitHub Actions. Перед подключением MAX нужно отдельно проверить выбранный сервер, HTTPS и реальные ответы. Контрольная сумма образа публикуется вместе с файлом.

## Проверка перед подключением

`python3 -m vneurok.readiness --env-file .env` проверяет только местный файл и форматы настроек, не выполняет команды из файла, не выводит токен и ничего не отправляет. Полный порядок: [LAUNCH_CHECKLIST.md](LAUNCH_CHECKLIST.md).

MAX использует `https://platform-api2.max.ru`. На выбранном сервере надо проверить доверие к TLS-цепочке этого API. Отключать проверку TLS нельзя. Если требуется дополнительный доверенный сертификат, его происхождение и изменение доверия согласовываются отдельно; код сам ничего не устанавливает.
